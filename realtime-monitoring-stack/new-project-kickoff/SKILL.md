# 起手一个「数据采集 + 展示 + 本地模型」类项目

**什么时候读这份**：接到一个"要做一个新系统"的需求，准备建目录、选架构、写第一批代码之前。

**适用范围**：适用于**从零起手**或**接手一个已有系统**的同类项目——数据从设备/服务实时进来、需要展示给人看、可能再叠一层本地模型做问答。不限特定编程语言或目录。

**这份东西的性质**：下面是**一个项目**跑出来的经验，不是通用最佳实践。凡是"当时这么定的"，都标了 `【一次性】`——那些决定有它的上下文，换项目要重新判断，**别照搬**。

> 如果你是**接手**一个已有项目，先读 `project-handover`——那份讲"该向人索取什么"，比这份更靠前。

---

## 一、起手顺序（先问清楚，再动手）

一个真实案例：最初的需求是一句话——「新建一个叫『XX监测』的文件夹」。最后做成了一个完整系统。**中间的价值不在写代码，而在每一步都先把"事实"和"假设"分开。**

按这个顺序推进，每一步都有明确产出：

1. **先确认能不能拿到数据**，再谈怎么展示
   - 第一个动作应该是**实测连通并抓一帧真实数据**，而不是先画界面
   - 拿不到数据的话，后面全是空转
   - **别信文档**：真实案例里接口文档没写"数据只在某个 topic、另一个是空的"——那是实测出来的

2. **把数据集的"物理含义"讲清楚**，再设计界面
   - 采样间隔、时间尺度、字段单位、**能测什么 / 不能测什么**
   - 真实案例里"采样 12.7 秒 ⇒ 不可能记录地震"这个结论，直接决定了后来不能做地震报警——**如果先做界面，会白做**

3. **先要"能不能"，再要"好不好"**
   - 用户在真实案例里明确说过「先做个能展示 X 的前端，其它功能先不要做。我看了效果没问题再进入下一步」
   - **照做**。一次只交付一层，等确认再往上加。

4. **数据量要提前算，因为它决定架构**
   - 「每天只保存这些点的数据，量有多大」这个问题定了量级，也定了后面用**定长二进制而不是 JSON**

5. **有歧义就问，别猜**
   - 真实案例靠**一轮一轮核对**（人报规则 → AI 画出来 → 人查错 → 修正）才把上百个点位对齐
   - 猜错的最坏后果是**看起来对的错**——比报错危险得多

## 二、可复用的架构骨架

### 2.1 一个进程干完所有事

**前端静态文件、采集、落盘、API 全部由同一个后端进程托管。**

这不是"图省事"，是为了避免一类具体故障：

> 真实案例早期前端由一个独立静态服务托管在 A 端口，后端 API 在 B 端口，而文档里写的入口是 A。后来那个静态服务没起，用户打开就是 `ERR_CONNECTION_REFUSED`；即使起起来，页面也是空的（静态服务没有数据接口）。**用户和 AI 都会记错端口。**

一个进程 = 一个端口 = 一个真相。前端用**同源相对路径**调 API，连 CORS 都不用配。

### 2.2 按时段分目录 + 定长二进制 + 索引

```
data/<时段>/
  <通道>.bin        # 定长记录（float32 等），按通道
  index.jsonl       # 每条一行：序号、时间、校验和、字节数
  manifest.json     # 通道数、每通道点数、记录长度
  report.md         # 该时段自动生成的报告（可选）
```

- 定长记录 ⇒ 想读第 N 条直接 `seek(N * recordBytes)`，不用解全文件。真实案例读最近 60 帧只要 5 ms
- `index.jsonl` 是唯一的"记录数"真相源；二进制长度也能反推，**两者不一致时以短的为准并截断**
- **目录加锁**（`O_EXCL` 原子创建 `.lock`）。真实案例出过事故：两个采集进程写同一目录，序号互相覆盖。只靠"读文件→判断 pid→写文件"有 TOCTOU 窗口，**必须用 `O_EXCL`**
- **开机自修复**：尾部不完整记录截掉、多通道记录数不一致截到最短、索引行数多于记录数则截断。**宁可丢一条，不能让整个文件读不了**

### 2.3 统计口径要能在重启后自洽

一个具体的坑：**进程内计数器**（"本次启动后写了多少"）和展示层的**"该时段已存多少"**是两个不同的量。真实案例把它们搞混过——重启后已存的 670 条显示成 4 条，**看起来像数据丢了**。

做法：

- 统计对象按**时段**存，**打开目录时用已存在的记录数回填**
- 进程级计数**单独一个字段**，名字要能一眼区分（如 `framesSinceStart` vs `framesRecordedToday`）
- **开机就预打开当前目录**，否则重启后到第一条数据到达之间还会有一段窗口显示 0

### 2.4 本地模型：数字只能有一个来源

如果要用本地模型做问答：

- **环境上下文里只放常量，不放会变的数字**（今天几号、有哪些日期、判据口径、点位总数）
- **所有数值由模型调工具去取**。一旦上下文里预置了数字，同一个问题会出现两条路径、两个答案
- 工具返回**纯文本而不是 JSON**（读标签文本比读 JSON 稳，token 也少）
- 数值算法**必须复用同一个函数**，否则聊天回答和自动报告会对不上
- **工具的描述会被模型当成系统规则**：参数说明写了「最大 31」，模型答出「系统仅保留最近 31 天」。**参数描述要写明"这是参数上限，不是系统策略"**
- 字段名**要带时间窗**：一个叫「速率」的字段，模型会读成"最近一小时的速率"——实际是全天回归斜率。改名「全天速率」才解决
- **提示词管不住的部分只能用代码兜**：真实案例里"模型没查数据就报数"，提示词写死了也拦不住，最后在代码层加兜底（本轮没调工具却出了数字 → 退回重答一次）

## 三、方法论（与项目无关，换什么都成立）

### 3.1 只声明"已完成"不算完成

用命令实测，给出输出。涉及路径的改动要在**新位置实际跑一次**，不是只看代码。涉及统计数字的改动，用**单次遍历 + 剪枝**，不要用会重复计数的写法——真实案例里出现过多次"统计脚本自身有 bug"。

### 3.2 发现异常时，先问"是产品错了还是我的检查器错了"

真实案例做模型回归测试时，**检查器自己的误报比产品 bug 还多**：连着 4 轮把模型的**正确拒答**判成违规。

根因：模型拒答时的固定写法是「引用用户的说法，然后否定它」——

> 工具未给出判据"一切正常"。因此**无法**断言"今天的数据一切正常"。

引号里那串正是违规词本身。往否定词白名单里补词补了 4 轮还是在打地鼠，最后改成**先剥掉引号内容再判**，一次就干净了。

**教训**：连续几轮都在"给检查器打补丁"时，说明**判定模型本身错了**，该换模型而不是继续补。

### 3.3 消误报之后必须做反向验证

放宽判定很容易把**真检测能力一起削掉**。必须补一组"真违规还抓得到吗"的用例，**正反都过**才算改完：

```
PASS  真违规·正常性结论     标记=true
PASS  真违规·工程建议       标记=true
PASS  拒答·正常性          标记=false
PASS  引述·正常性          标记=false
```

### 3.4 根因优先于打补丁

**同一个症状补了三次以上，停下来问：是不是抽象层次选错了。**

### 3.5 改了提示词 / 工具描述，要重跑同一套回归

措辞的敏感度远超直觉。真实案例的实测：

| 提示词 | 结果 |
| --- | --- |
| 「你可以调用工具查询数据。需要数据时先调用工具。」 | ✓ 调用 |
| 「你没有任何数据，必须调用工具才能获得数据。不得凭空回答。」 | **✗ 拒绝**，回「我目前没有这个功能」 |

**清单式肯定句有效，禁止式反而会让模型拒绝使用工具。**

所以：定一套固定的回归问题，每次改完重跑，**看数量而不是看感觉**。

> **注意**：不同模型对这些措辞的反应差别很大。上面的结论来自某一个具体模型，**换模型要重新测**，当"要测的清单"用而不是"已知结论"。

### 3.6 大输出落盘，别用管道截断

见 `windows-sandbox-hazards` 第 2.3 条。退出码 0 不等于成功，产物要校验。

## 四、明确标注为「一次性」的选择

下面这些是**那个项目当时的选择**，换项目要重新判断，**不要照搬**：

- `【一次性】` 突变判据取 2.5、色标取 ±3 —— 针对那台解调仪的量测噪声定的
- `【一次性】` 采样 12.7 秒、3 个通道、4773 个传感点 —— 那台设备的实测参数
- `【一次性】` 前端用 SSE 而不是 WebSocket 做实时推送 —— 因为是**单向广播**，SSE 更简单；**双向交互就该换**
- `【一次性】` 本地模型的具体选择 —— 受那台机器的显存限制
- `【一次性】` 44 GB/年 的存储方案 —— 是"存全部原始点"的代价，只存子集会小两个数量级
- `【一次性】` 3D 用 three.js —— 需求是"立体建筑 + 点位"，别的场景不一定需要
