# 接手项目：先向人要什么

**什么时候读这份**：拿到一个"照这个做一套"或"接着这个系统往下做"的任务，**在动手写任何代码之前**。

**为什么这份排在最前面**：代码和架构都可以重建，**但有几类东西 AI 自己拿不到**——

- 设备/服务的**真实行为**（文档常常没写全）
- 人**看图、看设备、跑一遍业务**之后得到的结论
- 这个领域里**"不能做什么"**的边界
- 委托方的**协作习惯**

缺了这些，你会做出"看起来对、实际错"的东西。真实案例里，最大的三次停顿**全都不是编码问题**。

**一句话**：**最该拿到的是"人已经想清楚的东西"，而不是代码。**

---

## 一、数据源实测表

> 原始文档**通常不够用**。真实案例里接口文档没写"数据只在 A topic、B topic 是空的"——那是实测出来的。只给文档，第一步就会走偏。

| 项 | 填什么 | 不给会怎样 |
| --- | --- | --- |
| 连接信息 | 地址 / 端口 / 账号 | 接不上 |
| **数据在哪个 topic / 端点** | 逐个确认**哪个有数据、哪个是空的** | 订阅错了会以为"设备没在发数据" |
| **有没有历史数据** | 有无 retained / 持久化 / 可回溯窗口 | 会去实现一个根本拿不到的功能 |
| **采样间隔** | 均值 / 中位 / 范围 | **决定能不能做某类事**（见下） |
| 多路时间对齐 | 各通道时间差多少 | 对齐口径错，数据对不上 |
| 单条大小 / 总量 | 字节数 / 点位总数 | 无法定存储方案 |
| **字段含义与单位** | 每个字段是什么、什么单位 | 会把"一维桩号"当成"空间坐标"之类 |
| 数据质量已知问题 | 已知的伪值、跳变、断线 | 会把设备问题当成业务现象 |

**采样间隔为什么单独强调**：它直接决定**物理上能不能测到某类现象**。

> 真实案例：采样 12.7 秒 ⇒ 奈奎斯特周期 25.4 秒 ⇒ 一次地震只会被采到 1~3 个混叠样本 ⇒ **这套系统不可能记录地震**。如果先做界面，会做出一个"看起来能报地震"的东西——那是错的，而且没人会发现。

**怎么拿到**：写探测脚本实际连一次、抓若干帧、统计。**不要靠读文档推断。**

## 二、人工核对结论表

> 这是**最该索取、也最容易被忽略**的一项。

有些信息**人看一眼就知道，程序要费很大劲还不一定对**——图纸标号、设备编号与业务编号的对照、业务规则的细节。

**正确做法**：请人把他的结论**以表格形式**给你，程序只在"需要批量、精确、可复现"的地方发力。

| 实体 | 业务编号 | 设备/系统编号 | 位置 | 备注 |
| --- | --- | --- | --- | --- |
| … | … | … | … | 哪些编号**没有**对应实体 |

真实案例的教训：

- AI 尝试**自动推导**编号规则，**全错**。人叫停后改成逐层人工核对才对齐
- 人自己打开图纸看完，直接给出结论（`「停止上面的所有工作，我已经看了施工图」`）——**这一句把项目从弯路拉回正轨**

**为什么自动推导必错**：编号规则是**图纸/业务约定**，不是能从几何或数据里推出来的。AI 越"聪明"地猜，产生的**"看起来对的错"越多**——这类错误在界面上不报错，只会静静地把东西标错位置，**而且不会被发现**。

**要一起索取的还有"约定"**：

- 方向 / 坐标轴约定（真实案例里方向反过一次，整层点位整齐镜像，单看每个点都"合理"）
- 单位与精度
- 分组规则、层级命名
- 哪些位置**故意没有**实体（缺号）

## 三、边界与验收表

> 这一节防的是**做出不该做的东西**。

| 类别 | 要问的 | 例子（真实案例） |
| --- | --- | --- |
| **物理/技术边界** | 这套系统**做不到**什么 | 采样率决定的"测不到地震" |
| **口径边界** | 哪些数字只是**显示口径**，不是判据 | ±3 / 2.5 只是显示阈值；材料极限差**三个数量级** |
| **禁止概念** | 明确**不要**引入什么 | 用户连续三次否决"故障点"概念——系统没资格替人下结论 |
| **验收标准** | 怎么算做对了，**要具体到可对照** | 「提示框要和真实鼠标悬停一样效果」 |
| **交付节奏** | 一次交多少 | 「先做 X，其它功能先不要做，我看了没问题再下一步」 |

**「显示口径 vs 工程判据」这条要反复确认并写进提示词**。真实案例里，显示阈值被误读成安全线是最容易发生的错误，也是后来本地模型问答里最硬的一条约束。

## 四、协作偏好

> 真实案例里**几乎所有的返工都跟这一节有关**，值得单独问清楚。

| 项 | 要问的 | 真实案例的表现 |
| --- | --- | --- |
| 交付粒度 | 一次交付多少 | 「一次只交付一层，等确认再往上加」 |
| **"问"和"做"的区分** | 是否要求严格区分 | 「回答我即可，不用动手」这类限定出现 **16 次**——**要照办** |
| 要不要主动加功能 | 可以自作主张到什么程度 | 主动引入的概念被连续否决三次 |
| 表达偏好 | 要解释还是直接给结果 | 多次要求"先解释、再让我选"，而不是直接定 |
| 数值偏好 | 谁来定主观值 | 报警色这种主观项，用户直接给了精确 RGB |

**默认假设**：**不要主动扩大范围**。想加功能先问。

## 五、建议的索取与交付顺序

按认知顺序来，**不要一次全倒**：

```
① 数据源实测表        -> 先确认"数据拿得到、是什么"
② 人工核对结论表      -> 跳过最难的推导环节
③ 边界与验收表        -> 划出不能做什么
④ 协作偏好           -> 定节奏
⑤ 原始文档/图纸/代码   -> 作为核对依据，不是主要输入
```

**第 ⑤ 项放最后是有理由的**：真实案例正是因为**先啃原始文件而绕了远路**，直到人工看图才走上正轨。新项目应该反过来——**以人的结论为主，原始文件为核对**。

## 六、不该要的 / 要重验的

**不要照搬上一个项目的**：

- 阈值、单位口径 —— 是针对**那台设备**的噪声定的
- 采样参数、通道数、点位数 —— 那台设备的实测值
- 具体的库 / 模型 / 端口选择 —— 受当时环境限制
- 存储量级结论 —— 是"存多少"的代价，换个范围差几个数量级

**必须重新验证的**：

1. **环境类陷阱**：换机器、换 AI 平台，沙箱约束和编码环境都不同 → 当**待验证清单**用
2. **提示词/措辞的敏感度**：不同模型反应差别很大 → 当**要测的清单**用，不是结论
3. **性能数字**：读取耗时、吞吐 —— 换设备/换数据量就会变

## 动手前自检

- [ ] 数据源**实际连过**了吗？抓的是真实数据不是文档推断吗？
- [ ] 拿到**人工核对过的对照表**了吗？还是打算自己推导？
- [ ] 「做不到什么」「什么只是显示口径」问清楚了吗？
- [ ] 有明确**禁止引入**的概念吗？
- [ ] 验收标准具体到可对照吗？
- [ ] 交付粒度和"问/做"的区分问清楚了吗？
- [ ] 有没有把上一个项目的**一次性数值**当成通用参数？
